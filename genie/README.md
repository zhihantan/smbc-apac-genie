# Genie spaces: authoring format (Phase 7)

Each of the 11 Genie spaces ("APAC Genie - ...") is built from two files you write by hand:

```
genie/
  README.md                      this file
  _shared.yaml                   shared settings: catalog, warehouse, the §8 base instruction block, as-of
                                 and response lines, shared helper functions, limits (do not edit per space)
  _schema/<fqn>.json             GENERATED column snapshot of every asset (written by the gate, read by the builder)
  <slug>/
    space.yaml                   AUTHORING SOURCE: title, description, data sources + column configs,
                                 instructions, example SQL, SQL functions, sample questions, benchmarks
    functions.sql                AUTHORING SOURCE: this space's UC SQL table functions (smbc_genie.gold.fn_*)
    space_id                     GENERATED by --create: the id of OUR space (never edit, never reuse)
    space_spec.json              GENERATED: brief Appendix B shape (human-readable summary)
    instructions.md              GENERATED: the rendered text instruction block
    benchmarks.json              GENERATED: {id, key, question, expected_sql, expected_checks, ...}
    <slug>.geniespace.json       GENERATED: the exact create/update body incl. serialized_space v2
    eval_report.json             GENERATED by --evaluate: per-question verdicts of the last evaluation
```

Slugs and titles are fixed (brief Appendix D, `smbc_genie_lib.metrics.SPACES`); the title must be exactly
`APAC Genie - <Topic>`. The reference implementation is `genie/early_warning_monitoring/`.

## What the builder does for you (so you never do it by hand)

- **Ids:** every list item gets a deterministic 32-hex id from (slug, kind, position), so the lists are already
  sorted in your authoring order (the UI shows sample questions in id order) and rebuilds are diff-free.
- **Sorting:** tables by `identifier`, `column_configs` by `column_name`, everything else by `id`
  (`smbc_genie_lib.genie.sort_serialized_space`; the API rejects unsorted lists).
- **Metric views go in `data_sources.tables`** (DECISIONS D42: the server normalises them there; sending them
  under `metric_views` breaks the round-trip diff).
- **Column configs for every column** of every asset, from the `_schema` snapshot: format assistance on for all
  STRING columns (PLAN §9), entity matching only where you ask, `exclude` where you ask.
- **Instructions:** one text block = `_shared.yaml` base block (10 lines) + as-of line + your domain lines +
  the response line. Multi-line strings become arrays of lines.
- **Expected SQL** can be pulled from `metrics/_answers/<slug>.sql` by question id (`answer: Q3`), so the
  benchmark and the must-answer query never drift apart.

## space.yaml reference

| Key | Required | Meaning |
|---|---|---|
| `slug` | yes | = folder name (Appendix D) |
| `title` | yes | exactly `metrics.SPACES[slug]`, e.g. `APAC Genie - Early Warning Monitoring` |
| `description` | yes | 2-3 sentences, brief §8 template (`_shared.yaml: description_template`) |
| `data_sources` | yes | list of assets (≤ 12): the space's metric views + drill-through tables (gold only) |
| `data_sources[].identifier` | yes | fully-qualified name, e.g. `smbc_genie.metrics.mv_ews_scores` |
| `data_sources[].columns` | no | `{<exact column name>: {synonyms, description, entity_matching, format_assistance, exclude}}` |
| `data_sources[].include_columns` | no | whitelist: every other column of the asset gets `exclude: true` (use on wide tables such as `vw_client_360`) |
| `instructions.domain` | yes | ≤ 8 one-line strings, each starting with `- ` (the builder adds base + as-of + response) |
| `instructions.response` | no | override the shared closing line (rarely needed) |
| `example_sqls` | yes | 4-6 parameterised example queries (trusted assets) |
| `example_sqls[].question` | yes | the question the SQL answers; use the parameter names in it, e.g. `EWS timeline for :client_group` |
| `example_sqls[].usage_guidance` | yes | one sentence: when Genie should use this query (phrasings, jargon) |
| `example_sqls[].parameters` | when the SQL has `:name` | `[{name, type, description, default}]`; `type` STRING or DATE (see limits) |
| `example_sqls[].sql` | yes | the SQL (block scalar `|`); every `:name` must be declared and vice versa |
| `sql_functions` | yes | fully-qualified function names: 2-3 defined in this space's `functions.sql`, plus optional shared helpers (`_shared.yaml`) |
| `sample_questions` | yes | 6-8 strings, in display order |
| `benchmarks` | yes | 12-20 items, see below |

**Column config keys** (all optional; omit a column to get the defaults):

| Key | Default | Notes |
|---|---|---|
| `synonyms` | none | ≤ 10, space-level extra synonyms (metric-view synonyms from UC are already visible to Genie - add only what is missing) |
| `description` | none | space-level description; leave empty when the UC comment is good (it is shown to Genie anyway) |
| `entity_matching` | false | value dictionary; STRING columns with ≤ 1,024 distinct values of ≤ 127 chars; ≤ 120 per space |
| `format_assistance` | true for STRING | sample values; forced on when `entity_matching` is on |
| `exclude` | false | hide the column from Genie |

**Benchmark keys:**

| Key | Required | Meaning |
|---|---|---|
| `key` | yes | stable human handle, unique in the space: `Q<n>` for must-answer n, `Q<n>-casual`, `Q<n>-abbrev`, `Q<n>-typo`, `Q<n>-jargon` for variants, `X<n>` for extra questions |
| `question` | yes | the user's wording (variants: casual, abbreviated, a typo, banker jargon) |
| `answer` | one of | question id in `metrics/_answers/<slug>.sql` (e.g. `Q2b`); its SQL becomes the expected SQL |
| `expected_sql` | one of | inline expected SQL (when no answers-file query fits) |
| `variant_of` | no | `key` of the benchmark this rephrases; inherits `answer` / `expected_sql` / `checks` unless set |
| `checks` | no | `{rows, min_rows, max_rows, must_contain_columns: [...], top_row_contains: "..."}` applied to the expected SQL's result; with `answer:` the default is `rows: <the answers file's -- rows: n>` |
| `allow_extra_columns` | no | true only for genuinely ambiguous questions: extra Genie columns then still pass (see the comparison rule below) |

## functions.sql rules

- One `CREATE OR REPLACE FUNCTION smbc_genie.gold.fn_<name>(...) RETURNS TABLE (...) COMMENT '...' RETURN ...;` per
  function, separated by `;`. Name prefix `fn_`, schema `gold`, and a **COMMENT on the function** (Genie cannot see
  the body) plus a `COMMENT` on every parameter and returned column.
- Read metric views (`MEASURE()` works inside a SQL UDF) or gold. Never `CURRENT_DATE()` (use `DATE'2026-09-30'`
  or `smbc_genie.gold.fn_as_of_date()`).
- **Arguments are STRING only.** Genie rejects a function with a `DATE` argument *at question time* ("certified
  answer argument type is not supported: date") and then fails **every** question of the space, although the
  create API accepted it. Take dates as `STRING` ('2026-01-01') and `to_date()` them inside; the builder errors on
  DATE / TIMESTAMP / ARRAY / MAP / STRUCT arguments and warns on other non-STRING types (unverified).
- **Reference the arguments only in the outermost query.** Inside a CTE over a metric view they fail with
  `ACCESSING_OUTER_QUERY_COLUMN_IS_NOT_ALLOWED`; compute the CTEs unfiltered and filter in the final `WHERE`
  (see `early_warning_monitoring/functions.sql`, `fn_ews_timeline`).
- No apostrophes inside `COMMENT '...'`: Databricks reads `'it''s'` as two adjacent literals ("its"). Rephrase.
- Add `-- test: SELECT * FROM smbc_genie.gold.fn_x('...')` lines: `--create` runs them after deploying and each
  must return at least one row.
- Arguments are the space vocabulary: `client_name STRING` (matched with `lower(x) LIKE lower(concat('%', client_name, '%'))`),
  `from_month STRING` ('2026-01-01'), `fiscal_year STRING` ('FY2026').
- `--create` deploys the file (CREATE OR REPLACE) before creating / updating the space. Functions for your space
  only; never touch another space's `fn_*` or the shared helpers.

## Commented skeleton (copy into genie/<slug>/space.yaml)

```yaml
slug: early_warning_monitoring                       # = folder name (brief Appendix D)
title: APAC Genie - Early Warning Monitoring         # exactly metrics.SPACES[slug]
description: >-                                      # brief §8 template, 2-3 sentences
  Ask about early-warning scores, signals, watchlist actions and delinquency for SMBC's APAC clients. Figures
  are USD unless you ask for local currency; periods follow the Japanese fiscal year (Apr-Mar). Client names
  roll up to client groups; data is synthetic and as of 30 Sep 2026.

data_sources:                                        # <= 12 assets; metric views first, then drill-through tables
  - identifier: smbc_genie.metrics.mv_ews_scores
    columns:                                         # exact column names (backtick names in SQL)
      Daily EWS Band: {entity_matching: true}        # low-cardinality labels: value dictionary
      Override Reason: {entity_matching: true}
      Client Days: {exclude: true}                   # hide measures that confuse more than they help
  - identifier: smbc_genie.gold.dim_ews_trigger
    columns:
      trigger_code: {entity_matching: true, synonyms: [UTILISATION_GT_90, COVENANT_BREACH]}
  - identifier: smbc_genie.gold.vw_client_360
    include_columns: [golden_client_id, display_name, short_name, group_name, coverage_office, ews_band]

instructions:
  domain:                                            # <= 8 lines; base block + as-of + response are added
    - "- Scores and bands: filter Date = DATE'2026-09-30' for today; Red >= 70, Amber 40-69, Green < 40."
    - "- 'Moved Green to Amber' = MEASURE(`Moved Green to Amber 30D`) on Date = DATE'2026-09-30'."

example_sqls:                                        # 4-6, each tied to a must-answer question
  - question: EWS score by month for :client_group since :from_month
    usage_guidance: Use for "walk me through <client>'s EWS score", "EWS history / timeline of <client>".
    parameters:
      - {name: client_group, type: STRING, description: "Client group or entity name fragment", default: Sunda Energi Nusantara}
      - {name: from_month, type: DATE, description: "First month (first day of month)", default: "2026-01-01"}
    sql: |
      SELECT `Month`, MEASURE(`Latest Score`) AS month_end_score
      FROM smbc_genie.metrics.mv_ews_scores
      WHERE `Client Group` LIKE CONCAT('%', :client_group, '%') AND `Date` >= :from_month
      GROUP BY ALL
      ORDER BY `Month`

sql_functions:                                       # 2-3 from functions.sql (+ optional shared helpers)
  - smbc_genie.gold.fn_ews_timeline
  - smbc_genie.gold.fn_as_of_date

sample_questions:                                    # 6-8, display order
  - Which clients are Red today and what are their top three triggers?

benchmarks:                                          # 12-20: every must-answer question + phrasing variants
  - key: Q1
    question: Which clients are Red today, what exposure do they carry, and what are the top three triggers for each?
    answer: Q1                                       # expected SQL = Q1 in metrics/_answers/<slug>.sql
    checks: {min_rows: 1, must_contain_columns: [Client, exposure_usd]}
  - key: Q1-casual
    question: who's in red right now and why
    variant_of: Q1                                   # inherits answer + checks
  - key: X1
    question: How many clients are Red today?
    expected_sql: |
      SELECT MEASURE(`Clients Red`) AS clients_red
      FROM smbc_genie.metrics.mv_ews_scores WHERE `Date` = DATE'2026-09-30'
    checks: {rows: 1}
```

## Limits (enforced by the builder; `_shared.yaml: limits`)

| What | Limit | Source |
|---|---|---|
| Assets (metric views + tables) | ≤ 12 per space | brief §3.4 (API: 50) |
| Text instruction | exactly 1 block, ≤ 20 lines (10 base + 1 as-of + ≤ 8 domain + 1 response) | brief §3.4, PLAN §9 |
| Instructions | ≤ 100 per space = example SQLs + SQL functions + 1 | API |
| Example SQLs | 4-6 | brief §3.4 |
| Space SQL functions | 2-3 (plus shared helpers) | brief §3.4 |
| Sample questions | 6-8 | brief §3.4 |
| Benchmarks | 12-20 (API ≤ 500), exactly one SQL answer each | brief §3.4 |
| Entity matching | ≤ 120 columns per space, ≤ 1,024 distinct values per column, ≤ 127 chars per value | API |
| Synonyms | ≤ 10 per column | brief / metric-view rule |
| Param type hints | `STRING`, `DATE` verified end to end; `INTEGER`, `DECIMAL`, `DOUBLE`, `BOOLEAN` accepted by the API; `INT`, `BIGINT`, `NUMBER`, `NUMERIC`, `FLOAT`, `TIMESTAMP` are **rejected** | probed 2026-10-04 |
| SQL function arguments | STRING only (DATE breaks the whole space at question time) | probed 2026-10-04 |
| SQL | no `CURRENT_DATE()` / `NOW()`; only the space's own assets and listed functions may be referenced; 5-minute timeout | D16, API |

Client names (2,552 golden clients) exceed the 1,024-value dictionary limit: never set `entity_matching` on
`Client` / `display_name` / `legal_name`; teach `LIKE '%…%'` in example SQL instead. Client Group (~380),
Primary RM (~120), Coverage Office (13), Industry, Segment, bands, triggers, reasons and other labels fit.

## Do's and don'ts

Do:
- Answer must-answer questions from the metric views with `MEASURE()`; benchmark expected SQL names its output
  columns (`AS exposure_usd`) and is minimal (D30): only the columns the question asks for.
- Phrase benchmark questions so the expected result is unambiguous (date, grain, entity vs group, top N).
  Grading compares result sets: order-insensitive, 4 significant digits, extra rows or columns are wrong.
- Write one variant per style for the key questions: casual, abbreviated, a typo, banker jargon
  (utilisation, headroom, RoRWA, CASA, DPD, WL, RAG).
- Put caveats from `scratch/genie_caveats.md` where Genie needs them: a field comment or synonym first, an
  example SQL second, a domain instruction line last (PLAN §9 fix order).
- Teach cross-view questions with one example SQL that wraps each metric-view query in a CTE and joins the
  CTEs (D35).
- Keep point-in-time filters explicit in example SQL: `` `Date` = DATE'2026-09-30' `` or `` `Is Latest Month` ``.

Don't:
- Don't add bronze, silver, shared or ops objects; gold and metrics only.
- Don't enable entity matching on client names, ids or free text.
- Don't write more than 8 domain lines or restate the base block - it is added for you.
- Don't edit `space_id`, the generated JSON files or another space's folder.
- Don't touch Genie spaces that are not titled `APAC Genie - ...`, don't change permissions or share spaces.
- Don't edit metric-view logic; additive metadata (comments, display names, synonyms ≤ 10) in your own space's
  `metrics/<view>.yaml` only, rebuilt with `run_metrics.py --only <view> --skip-invalid` to 0 problems.

## Runner (`src/50_genie/run_genie.py`)

```bash
P="--profile my-workspace"
.venv/bin/python src/50_genie/run_genie.py --build-only --only <slug>              # offline: validate + write artefacts
.venv/bin/python src/50_genie/run_genie.py $P --only <slug> --dry-run              # read-only: gate + diff vs the live space
.venv/bin/python src/50_genie/run_genie.py $P --only <slug> --dry-run --evaluate   # read-only: expected-SQL checks only
.venv/bin/python src/50_genie/run_genie.py $P --only <slug> --create               # functions + create/update + round-trip + smoke question
.venv/bin/python src/50_genie/run_genie.py $P --only <slug> --evaluate --label "iteration 1"   # benchmarks -> ops.genie_benchmarks
```

| Flag | What it does |
|---|---|
| (none) | build + gate (refreshes `genie/_schema`, DESCRIBEs the assets, counts entity-matching values) + write artefacts |
| `--build-only` | offline build from the committed `_schema` snapshot; no login needed; exit 2 on spec errors |
| `--dry-run` | no writes at all: build + gate + the content diff against the live space (+ expected SQL with `--evaluate`) |
| `--create` | deploy `functions.sql` and run its `-- test:` probes, create or PATCH our space, GET it back and diff, ask one smoke question (first sample question) through the Conversation API, merge the benchmark catalogue into `ops.genie_benchmarks` |
| `--evaluate` | run every expected SQL and its checks, start an eval-run, grade, write `ops.genie_benchmarks`, `ops.build_run_log` (phase `p07_genie`), `genie/<slug>/eval_report.json` and append `eval_history.jsonl` |
| `--only a,b` | restrict to some slugs (`--spaces` is an alias; default = every `genie/*/space.yaml`) |
| `--eval-method` | `auto` (eval-runs, Conversation API if unavailable), `eval_runs`, `conversation` |
| `--no-smoke` | skip the smoke question after `--create` |
| `--skip-gate` | continue despite gate failures (development only) |

Exit codes: 0 ok (and pass rate ≥ 85% with `--evaluate`), 1 gate / create / evaluation problem, 2 spec errors.
Other entry points: `build_space_specs.py` (= `--build-only`), `metadata_gate.py` (`--snapshot-all` refreshes the
snapshot of every gold + metrics object), `run_benchmarks.py` (= `--evaluate`, used by the p08 job).

**Safety.** The runner only touches the space whose id is in `genie/<slug>/space_id`, or - when that file is
missing - the single space with exactly our title (then it writes the file). A tracked id whose title changed, or
several spaces with our title and no `space_id`, stop the run. It never changes permissions or shares a space.
Run evaluations one space at a time (rate limits are workspace-wide; the client backs off on 429 / 5xx).

**Iterating (PLAN §9 fix order, up to 3 rounds):** read `eval_report.json` (`reason` + `genie_sql` per question),
then fix in this order: metric-view metadata (comments / synonyms in your own views' YAML, additive only) →
space column synonyms / entity matching → example SQL → domain instruction lines. Re-run `--create` then
`--evaluate --label "iteration n"`.

### Lessons from the pilot (early_warning_monitoring: 70% → 95% → 100% over three evaluations)

- **One convention per space, and benchmarks that follow it.** A domain line "counts per group: only groups
  above zero (HAVING > 0)" made Genie drop zero rows everywhere, so expected SQL without the HAVING failed on
  row count. Write the expected SQL the way your instructions tell Genie to answer.
- **Minimal expected SQL + `allow_extra_columns` for list questions.** Expect only what the question asks
  (`Client`, the measure asked for); Genie adds Coverage Office, scores or counts. The question "Clients with X in
  the same month" was answered without `Month` - don't expect columns the question doesn't name.
- **Time filters leak.** "(`Is Latest Month` = today)" next to "actions overdue are as of today" made Genie filter
  the latest month for overdue actions (2 rows instead of 22). State "never filter Month for this measure" in the
  measure comment (additive metric-view metadata) and keep instruction lines free of such traps.
- **Trusted examples win when the wording overlaps.** "How many overrides cite JP parent support?" kept reusing the
  parameterised override-breakdown example. Keep example questions distinct from single-number questions and say
  in `usage_guidance` what the example is *not* for.
- **Functions make multi-part questions gradable.** The must-answer "walk me through X's EWS score month by month
  and which signals fired when" passes because the expected SQL and the example SQL both call
  `fn_ews_timeline('Sunda Energi Nusantara', '2026-01-01')`.
- Genie used `Is Latest Month` instead of `Date = DATE'2026-09-30'` for "today": both give the same result for
  window (point-in-time) measures, so either is fine in expected SQL.
- If **every** result is `EVALUATION_FAILED` / `EMPTY_RESULT`, the space configuration is invalid at question
  time (pilot: a DATE function argument); the `--create` smoke question shows the error message.

### Comparison rule (grading)

1. The eval-runs API (Beta, available on this workspace) grades each benchmark `GOOD`, `BAD` or `NEEDS_REVIEW`.
   `GOOD` passes.
2. Otherwise the runner re-executes Genie's SQL and compares it with the expected SQL's result:
   - order-insensitive: the same multiset of rows, and extra rows always fail;
   - values compared to 4 significant digits; booleans as true/false; midnight timestamps as dates;
   - columns are matched by their values (names and column order ignored);
   - extra columns fail unless the benchmark sets `allow_extra_columns: true`. Use that only for genuinely
     ambiguous questions, e.g. list questions where the base block makes Genie add Coverage Office.
3. `ops.genie_benchmarks` keeps both the API assessment (`last_eval_assessment`) and the final verdict
   (`last_eval_pass`, `eval_reason`). `space_pass_rate` = passes / benchmarks.

### Verified API behaviour (2026-10-04, this workspace)

- Create / PATCH / GET round-trip is content-identical, including column configs on metric-view columns
  (description, synonyms, entity matching, format assistance, exclude), parameter descriptions and
  usage_guidance. The only difference: GET returns `benchmarks.questions` in **descending** id order (the runner
  compares id-sorted).
- Parameter `type_hint` accepted: STRING, DATE, INTEGER, DECIMAL, DOUBLE, BOOLEAN; rejected: INT, BIGINT, NUMBER,
  NUMERIC, FLOAT, TIMESTAMP.
- SQL functions: STRING arguments work; a DATE argument breaks the whole space at question time (see above).
- Eval-runs: `POST /api/2.0/genie/spaces/{id}/eval-runs {}` → poll `GET …/eval-runs/{run}` (`eval_run_status`
  RUNNING → DONE, `num_correct`, `num_needs_review`) → `GET …/{run}/results` → `GET …/{run}/results/{result_id}`
  (`assessment`, `assessment_reasons`, `actual_response[].response` = Genie's SQL, both result sets). About
  15 s per question. A per-result `eval_run_status` of `EVALUATION_FAILED` with reason `EMPTY_RESULT` means
  Genie produced no answer at all: ask one question with `--create` (the smoke question) to see the error.
